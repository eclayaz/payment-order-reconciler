# Feature List — derived from evidence

Every feature below traces to a specific real failure mode (GitHub issue), a Stripe platform mechanic, or a WordPress/WooCommerce platform constraint. See [PROBLEM.md](./PROBLEM.md) for the underlying problem statement.

> Revised 2026-08-29 (first pass) after an independent technical review verified every hook name, meta key, and detection rule directly against the gateway plugin's actual source. Revised again 2026-08-29 (second pass) after a follow-up review found that several first-pass corrections were individually accurate but their consequences hadn't been traced into other sections — a hook nominated as the "primary signal" for a check it can structurally never fire in, an exclusion list that verified three false-positive sources but missed a fourth (open disputes) whose root cause was already documented one section earlier, and a fix action with three independent API-level bugs. Both passes' corrections are kept inline below.

## Detection layer

1. **Real-time hook listener** on `wc_gateway_stripe_process_webhook_payment_error` — fires at 7 call sites in the gateway's webhook handler, confirmed to exist by direct source inspection. **Correction:** this hook also fires on **dispute-created events** after an intentional on-hold transition — not only on genuine failures. The listener must filter by the notification/exception type passed to the hook, or it will manufacture false drift candidates out of normal dispute handling. **Correction:** every call site requires an already-resolved `$order` — when the gateway can't find an order at all (the actual orphaned-charge case), it logs a warning and returns *without* firing this hook. **This hook can never signal an orphaned charge** — that detection has to come from the bulk polling job below, not this listener.

2. **Real-time hook listener** on `wc_gateway_stripe_process_payment_charge` (success signal) — used **only to accelerate detection that a Pass A run would eventually confirm**, not as a standalone resolver. **Correction (second review):** this hook fires as the *first statement* of `process_response()`, before the charge is actually processed or committed — its own docblock says it exists to run custom logic "before processing the charge data from Stripe," and the code immediately following it can still throw. **Do not use this hook to auto-resolve open drift records** — a fix or a legitimately-completing order could still fail after this hook fires, and marking a drift record `resolved_by: system` at this point would be marking it resolved before the resolution actually happened. Use `woocommerce_payment_complete` for auto-resolution instead (see Fix actions below) — it fires only after WooCommerce core has actually committed the payment-complete transition.
   *Also corrected from the original draft:* the previously-specified hook, `wc_gateway_stripe_process_webhook_payment`, is **deprecated since gateway version 9.7.0**. `wc_gateway_stripe_process_payment_charge` is the non-deprecated replacement and fires from more call sites (including the redirect-based payment path), but per the correction above it's used here as a detection accelerator only, not a resolution signal.

3. **Real-time hook listener** on `wc_stripe_paid_order_cancellation_prevented` (added in gateway 10.8.0). **Corrected role (second review) — this was wrong in the first-pass rewrite.** The first-pass correction said this hook "should be the primary real-time source" for the narrowed wrongly-cancelled check (#6 below). That's self-contradictory: the hook fires **only inside the `if ( $order->get_date_paid( 'edit' ) )` branch** of the gateway's guard — i.e. only when `date_paid` *is* set. Check #6 exists specifically to catch orders where `date_paid` was *never* set, which is exactly the case this hook cannot fire for. The two claims can't both be true, and they aren't.
   **What this hook is actually good for:** (a) telemetry for the coverage/health dashboard — every firing is direct evidence the gateway's own 10.8.0+ guard is active and working on this store, which is useful to show merchants; (b) a real-time signal for stores that haven't upgraded past 10.8.0 yet, where an equivalent guard doesn't exist, is a distinct question this hook can't answer either (it requires the guard code itself, which only ships in 10.8.0+). *Also note (second review):* the gateway guards this hook to fire **once per order, ever** (`_stripe_paid_order_cancellation_prevented` meta short-circuits repeat firing) — it's a once-per-order event, not "whenever the guard trips," which matters if building a firing-count metric.

4. **Scheduled reconciliation job on ActionScheduler**, running two independent cadences rather than one (see TECHNICAL_SPEC.md for the full mechanism and the reasoning behind the two cadences):
   - **Incremental pass** (hourly, default): fetch only Stripe objects created since the last incremental run's high-water mark — cheap, catches new checkout activity promptly.
   - **Full resweep** (daily, default): re-pull the entire reconciliation window (default 30 days). *Added in the second review:* an incremental-only design misses **state changes on already-seen objects** — a dispute opened after the fact, a refund issued later, a cancellation that happens days after the PaymentIntent was created — none of which touch the `created` timestamp the incremental pass filters on. The daily resweep exists specifically to catch those.
   *Correction on framing (unchanged from first pass):* ActionScheduler's own queue runner is still triggered by WP-Cron under the hood (plus async loopback) — it does **not** fully solve the zero-traffic-site problem, it adds durability/retry/visibility on top. This makes the "last successful run" coverage indicator more important than originally scoped, not less.

5. **Two separate idempotency mechanisms — corrected (second review), the original single ledger doesn't cover the primary detection path.** The first-pass draft specified one event-ID ledger "shared between the hook listeners and the polling job." That only works for the hook listeners and the diagnostic Events poll (Pass B below), both of which have a Stripe event ID to key on. **Pass A (the primary bulk list-and-diff mechanism) lists PaymentIntents, which carry no event ID at all** — there is nothing for that ledger to dedup against. Two separate mechanisms are needed:
   - **Event-ID ledger** (not-processed / processing / processed), scoped to the hook listeners and Pass B only.
   - **A uniqueness constraint on `wsr_drift_log`** over `(stripe_object_id, drift_type)` where `status = 'open'` — this is Pass A's idempotency mechanism. Re-detecting an already-open drift updates its `detected_at` rather than inserting a duplicate row. Without this, every scheduled run (hourly or daily) would re-insert the same open drift as a new row.

## Reconciliation checks (each maps to a confirmed real failure class, with corrected detection logic)

6. **Wrongly-cancelled-paid-order detector** — targets the residual case: an order where the payment actually succeeded at Stripe but the order was never marked paid locally at all (so the gateway's own 10.8.0+ guard never engaged), then got auto-cancelled.
   *Corrected check logic (first pass):* PaymentIntent status is `succeeded` **and** the underlying charge's `captured` flag is `true` **and** `amount_refunded < amount`. (Removed a nonexistent `requires_capture`-with-captured-funds state from the original draft — see prior revision notes for why.)
   *Additional hard exclusion, added in the second review:* **`charge.disputed === true` must exclude an order from this check entirely.** An actively disputed charge stays `succeeded` with `amount_refunded` still at 0 (a lost dispute reverses funds outside the refund field, so the `amount_refunded` condition above doesn't catch it either) — meaning a disputed order that's sitting cancelled or on-hold would otherwise pass every other condition in this check. This is not a tuning nicety; see PROBLEM.md's non-goals section for why this is a hard v1 exclusion, not something to fix later.
   *Evidence:* [#5268](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5268) (fixed 10.8.0 — historical evidence of the failure class, not current), the SSSV report on #5691 (2026-08-14, on gateway 10.8.5, explicitly *not* the Checkout Session flow — see PROBLEM.md) where an order was still cancelled because it never reached `date_paid`.

7. **Stuck-pending detector** — flags when local order status is pending/on-hold but Stripe's PaymentIntent is `succeeded`, **excluding**:
   - Orders with `_stripe_payment_awaiting_action` meta set — **corrected to be time-bounded (second review), not a permanent exclusion.** The gateway's own guard only honors this meta for **24 hours** from the order's last modification (`get_date_modified() > -1 day`) before treating the order as abandoned rather than mid-3DS — its own docblock explains the reasoning. Excluding on the meta's mere presence, with no time bound, would create a permanent blind spot for exactly the drift class this plugin targets (a 3DS flow that actually did complete, but whose meta was never cleared). Mirror the gateway's 24-hour window: exclude only if the meta is set **and** the order was modified within the last 24 hours; treat it as eligible for detection past that window, same as the gateway itself does.
   - **`charge.disputed === true`** — added in the second review, same reasoning as #6 above: an open dispute puts an order on-hold with a still-`succeeded` PaymentIntent, indistinguishable from genuine drift under the base rule. This was the single highest-severity gap found across both review passes — the raw fact (disputes trigger an on-hold transition) was already documented in #1 above but hadn't been carried into this exclusion list until now.
   - Orders on-hold due to a Stripe Radar manual-review outcome (check `charge.outcome.type === 'manual_review'`) — intentional, not drift.
   - Orders on-hold by design under an authorize-and-capture setup, or awaiting an async payment method (ACH microdeposits, Multibanco, Boleto).
   - Orders with `_stripe_status_final` meta already set.
   *Evidence:* [#5691](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5691), [#5326](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5326) (Bancontact/APM charge-ID lookup race).

8. **Orphaned-charge detector — mechanism substantially corrected in the second review.** A settled Stripe payment with no matching local order, within the reconciliation window, is a candidate — but resolving "no matching local order" correctly turned out to be more involved than the first-pass draft assumed.
   *Join-key strategy, corrected order of preference:*
   1. **`metadata.signature`** (format `order_id:md5(order_id-order_key-customer_id-order_total)`, present on both legacy and UPE checkout paths) — parsing the leading segment yields the **internal order ID directly**, no local lookup query needed, and the md5 half doubles as a tamper/collision check.
   2. **`metadata.order_key`** (UPE path) as a fallback.
   3. **Cross-reference via Checkout Session** (see below) for the flow where neither of the above is present at all.
   *Corrected from the first-pass draft:* matching on `metadata.order_id` was wrong — the gateway writes the order's **display number** into that field, not the internal ID, and these diverge on any store with custom/sequential order numbering.
   *The Checkout Session gap, found in the second review and not present in the first-pass correction at all:* the Adaptive Pricing / Optimized Checkout Session flow — which is the actual root cause of the original #5691 report (see PROBLEM.md) — creates a PaymentIntent whose metadata carries **none** of `order_id`, `order_key`, or `signature`, because the session is built from the cart before an order exists. Under the join-key strategy above alone, every one of these PaymentIntents would be misidentified as an orphaned charge, on a real, evidenced flow. **This requires a separate mechanism**, detailed in TECHNICAL_SPEC.md: listing Checkout Sessions directly and cross-referencing session ID against the local `_stripe_checkout_session_id` order meta, rather than expecting the PaymentIntent alone to carry enough information.
   *Site scoping, corrected:* filter by `metadata.site_url`, but as a **host comparison with normalization** (www/non-www, http/https), not strict string equality — the first-pass draft's strict-equality version would silently drop legitimate payments across any domain change, which is a real scenario for exactly the kind of store likely to have accumulated drift. A PaymentIntent with `site_url` metadata **absent entirely** (a real, evidenced case per the Checkout Session gap above) must not be silently excluded either — treat it as `needs_review`, escalating to `orphaned_charge` only after failing to resolve on a second consecutive run, not immediately.
   *Evidence:* the root pattern behind the "stuck/missing order" issue family, the independently-reinvented fix in the "23 missing orders" blog post, and the Adaptive-Pricing-specific root cause on #5691 itself.

9. **Refund/capture drift detector** — evidence unchanged from prior revisions; date corrected below.
   *Evidence:* [#2799](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/2799) (open, created 2023, last updated 2026-08-18), [#5140](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5140) (fixed and released in 10.9.0), [#5699](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5699) — **date corrected (second review):** this was closed 2026-08-24, but its fix appears only in the unreleased `11.0.0-dev` changelog — it has **not shipped** in any released version as of this writing. Cite it as "fixed, unreleased," not simply "fixed."

10. **Idempotency-collision flag** (v1.5, low priority) — unchanged, confirmed real but rare/unquantified on inspection ([#4915](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/4915), tagged `priority: low`, `needs repro` by the maintainers themselves).

11. **Webhook setup/health check** — a real v1 feature (elevated from a footnote in the original draft). The #5691 thread's own root cause was a webhook endpoint pointed at a **stale staging domain**, not a code bug. A periodic validation that the configured webhook endpoint is reachable, live, and pointed at the current production URL catches this directly. *Scope requirement added in the second review:* this needs `GET /v1/webhook_endpoints`, which requires a **`Webhook Endpoints:Read`** restricted-key scope not listed in the first-pass draft's scope list — add it to the settings-screen onboarding instructions and the sandbox-verification task in TECHNICAL_SPEC.md.

## Explicitly NOT reconciliation-job features

- **Dispute-cascading-to-wrong-order** — **evidence-status correction (second review):** [#3556](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/3556) was listed as a "v2 candidate" without a state annotation, inconsistent with every other citation in this document. It is **closed** (2025-06-17). Kept as a v2 candidate since the underlying failure class (a dispute on one subscription renewal flipping an unrelated renewal to failed) is still instructive, but cited accurately as closed, historical evidence — not an open bug.
- **Stripe Radar false-blocks** — [#5601](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5601) is a feature request, [#5670](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5670) its merged implementation (a new hook, not a bug fix), #2679 an unrelated status-flip issue. Only [#5030](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5030) genuinely fits this category, and it's fixed. **Out of scope regardless** — checkout-time prevention bug class, not detectable after the fact by diffing state.
- **Test-mode/live-mode key mismatches** — folded into the webhook health-check feature (#11) rather than left as a vague deferred item.
- **Currency/multi-currency and UPE-migration frontend bugs** — real but checkout-UX/display bugs, not order-state drift. **Fully out of scope.** Even the in-scope checks need to be currency-aware for Stripe Connect/multi-currency stores (presentment vs. settlement currency, `_stripe_presentment_currency`/`_stripe_presentment_amount`) — document single-currency, non-Connect stores as the supported v1 configuration rather than silently mishandling the unsupported case. **Tension noted in the second review, not yet resolved:** the Checkout Session / Adaptive Pricing flow that #8 above requires special handling for **is itself the multi-currency flow this section defers**. v1 therefore needs the Checkout Session *matching* logic in #8 (to avoid false orphan-flagging) even while deferring full multi-currency *amount comparison* — these are separable: match the order first, then skip amount-based checks specifically (not the whole order) when presentment currency differs from the store's default.

## Fix actions — corrected, single-primitive design, now with three additional API-level corrections from the second review

**Original bug (first pass):** the original draft's fix design called `$order->update_status()` then manually re-fired completion emails/stock reduction — `update_status()` already triggers WooCommerce's own customer and admin emails and stock reduction on these transitions, so the manual re-fire would have double-sent every notification on every fix.

**Corrected primitive (first pass, still correct):** use `$order->payment_complete( $charge_id )` — works from `cancelled`/`pending`/`on-hold`/`failed`, sets `date_paid` and transaction ID, fires `woocommerce_payment_complete`, lets core handle stock/email exactly once.

**Three further corrections from the second review, all at the level of "the right primitive, called incorrectly":**

- **Lock check was actually a lock *acquisition*.** The draft specified checking `WC_Stripe_Order_Helper::lock_order_payment()` before applying a fix. That method doesn't check anything — it **acquires** a 5-minute lock and returns whether one was already held. Calling it as a "check" would silently take a lock the fixer never releases, blocking the gateway's own webhook processing for 5 minutes on every fix. **Corrected:** use the read-only accessors — `is_order_payment_locked()` / `get_order_existing_payment_lock()` — to check, and skip/defer the fix if locked rather than taking a lock of our own.
- **`payment_complete()`'s return value can't be trusted as a success signal.** It returns `true` on a no-op path (order already in a non-payable status) as well as on genuine success, and `false` only for a missing charge ID or a caught exception. **Corrected:** after calling it, re-read the order's actual status/`date_paid` before writing `fixed` to `wsr_drift_log` — the audit log is a trust feature and must reflect what actually happened, not what the call returned.
- **`payment_complete()` alone leaves Stripe-specific meta incomplete.** The gateway's own normal payment-processing path additionally sets `_stripe_charge_captured` (read by the gateway's own cancellation and refund logic) and clears `_stripe_payment_awaiting_action`. A fix that only calls `payment_complete()` leaves an order in the exact state described by **[#5699](https://github.com/woocommerce/woocommerce-gateway-stripe/issues/5699)** — one of this document's own cited failure modes — where a missing capture flag breaks wp-admin refunds. **Corrected:** the fixer must also write `_stripe_charge_captured = true`, set `_stripe_intent_id` if it was absent, and clear `_stripe_payment_awaiting_action`.

Fix-applied tracking uses a single `_wsr_fix_applied` meta key holding a JSON list of already-fixed `stripe_object_id`s, not a per-fix dynamic meta key. *Correction to the original rationale (second review):* the reason is **unboundedness alone** — a growing, uncleanable set of per-order meta keys over time. (The original draft additionally claimed the dynamic-key approach was "unqueryable," which is backwards — a JSON blob is *less* queryable than discrete keys, since no `meta_query` can index into it. The unboundedness argument is sufficient on its own; `wsr_drift_log` remains the authoritative, queryable fix history regardless, making this meta key a fast idempotency guard rather than a reporting source.)

Never calls a Stripe write endpoint — refund/void/charge actions remain permanently out of scope per the read-only trust model in PROBLEM.md.

## Reliability/safety features (corrected)

- Build the job on **ActionScheduler**, not `wp_schedule_event` directly — confirmed bundled with WooCommerce core and used internally by the gateway itself. Still ultimately WP-Cron/loopback-triggered underneath — see the coverage indicator below.
- No direct `$wpdb` queries against order or meta tables — use `wc_get_orders()`, `WC_Order_Query`, and core lookup helpers (e.g. `wc_get_order_id_by_order_key()`). *Correction (second review):* the first-pass draft cited the gateway plugin itself as an example of violating this ("HPOS-fatal"). On inspection, the gateway's raw-query code path only runs on **legacy** (non-HPOS) storage, branching correctly around HPOS — it isn't broken, and isn't something our plugin needs to avoid copying for the reason originally stated. The recommendation to avoid raw `$wpdb` queries stands on its own merits regardless.
- Detect environment via `wp_get_environment_type()` plus a fallback check, since it defaults to `'production'` when unset. **Key-prefix correction (second review):** the plugin holds a **restricted** Stripe key, so the relevant prefixes to compare are `rk_live_`/`rk_test_`, not `pk_live_`/`pk_test_` (publishable-key prefixes) as an earlier draft of this document said.
- Surface a **"last successful reconciliation run" indicator** as a primary dashboard element, not a footnote — the stores most likely to have this bug are also the ones most likely to have an unreliable scheduler.
- **Restricted-key scope verification, expanded (second review):** confirm directly against a sandbox restricted key which discrete resource scopes Stripe's restricted-key model actually exposes for **all four** v1-relevant resources before finalizing onboarding copy — `PaymentIntents:Read`, `Charges:Read` (needed regardless), plus `Events:Read` (gates the Pass B diagnostic), `Checkout Sessions:Read` (gates the Checkout Session cross-reference in #8), and `Webhook Endpoints:Read` (gates #11). The first-pass draft only flagged `Events:Read` as needing verification; the other two scopes were missed.

## Admin UX (dashboard)

- **Drift dashboard**: flagged orders grouped by category. **Correction (second review):** the category list must match what v1 actually produces — `refund-mismatch` is v1.1 scope (see #9/#10 sequencing) and should not appear as a v1 dashboard grouping until that check ships.
- **Webhook health status** (per #11) shown prominently, not buried in settings.
- **Email/Slack alert on new high-severity drift** — paid-tier feature per PROBLEM.md's monetization plan.
- **Audit log of every automated fix action** — what changed, when, from what state to what state, cross-checked against re-read order state (see Fix actions above), tied to the single `_wsr_fix_applied` meta key.

## Summary: what v1 must include, minimum (revised after second review)

Detection: hook listeners #1-#3 (used as accelerators/telemetry only, per the corrected roles above — none of them is a standalone resolver) + the two-cadence bulk-list-and-diff scheduled job (#4) + the two separate idempotency mechanisms (#5, since one ledger doesn't cover both detection paths).
Checks: **orphaned-charge (#8)** — now including the Checkout Session cross-reference, without which it false-positives on a real, evidenced flow — and the **narrowed wrongly-cancelled-paid check (#6)**, both with the `charge.disputed` hard exclusion. **Stuck-pending (#7)** ships with its full, corrected exclusion list (including the time-bounded awaiting-action window and the dispute exclusion) from day one — an incomplete exclusion list is actively harmful, not merely incomplete.
**Webhook health-check (#11)** ships in v1 alongside these.
Fix: `payment_complete()` plus the three corrected companion steps (lock-check via read-only accessor, post-call state re-verification, Stripe-meta completion) — not `payment_complete()` alone.
Everything else (refund-drift, idempotency-collision flag, dispute-cascade) remains real and evidenced but sequenced into v1.1+.
